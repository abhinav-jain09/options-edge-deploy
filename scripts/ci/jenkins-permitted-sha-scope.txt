# Scope of the Jenkins-side permitted-commit guard (Deployment Permission Rule, options-edge rule.md).
# Read by scripts/ci/validate-jenkins-permitted-sha-guard.sh. EVERY checked-in Jenkinsfile* ANYWHERE in
# the repository must appear here exactly once, by its repository-relative path — a Jenkins job's
# definition is a path, not a name, and a definition nobody classified is one nobody judged:
#   <path/to/Jenkinsfile> | in|out | options | reason
# options (semicolon-separated, may be empty):
#   before=<stage>,<stage>   stages allowed to run BEFORE 'Permitted commit guard' (an existing
#                            environment-branch refusal that must keep running first). Anything else
#                            before the guard fails the validator.
#   reguard=<stage>          the pipeline is `agent none` and its deploy stages run on their own agent
#                            inside <stage>; that stage's FIRST nested stage must be
#                            'Permitted commit guard (deploy workspace)' — the guard re-established in
#                            the workspace the effects actually come from.
# "out" means the job carries NO guard THIS VALIDATOR ACCEPTS OVER ITS EFFECTS, and therefore CANNOT be
# triggered by the assistant (rule line 364: "A job without this guard cannot be triggered by the
# assistant"); it stays Abhinav's manual job or a scheduled one. The reason says which and why.
# The qualification is not a loosening, it is the width of the claim. An `out` file is NOT rule-checked
# here, so nothing in this file is a statement that an `out` job is guard-conformant; and `--only`
# (scripts/jenkins/require-guarded-downstream.sh, a parent proving a child before it triggers it)
# REFUSES every `out` path by this classification alone, whatever the file contains. Most `out` jobs
# carry no guard at all. Jenkinsfile.rithmic-depth-bridge-release does carry one, over THIS repository's
# tree, and still cannot bind the foreign checkout its image is built from — which is exactly why it is
# `out`, and why "no guard" unqualified would have been the false half of a true conclusion. A guard in
# an `out` file buys only what it covers and is not validated here; where one exists, the job's own test
# is what keeps it canonical (tests/test_rithmic_es4_service.py for that file).
