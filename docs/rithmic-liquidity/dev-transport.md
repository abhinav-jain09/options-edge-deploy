# Dev Rithmic Kafka stream

The collector runs in ES4 Linux Kubernetes namespace options-edge and publishes canonical Avro depth frames to es.rithmic.depth. Two ES4 mirror pods preserve the raw topic name and copy it to dev and prod with durable offsets committed after delivery. The prod image registry is 192.168.100.252:5000. The existing es-spx-align service reads that topic and its existing global basis store, then writes options.rithmic.es-depth-spx. The feed gateway consumes the display topic and sends rithmic-liquidity events over its existing authenticated WebSocket. The web renders those events on the existing Order chart transforms.

There is no laptop runtime or SSH market-data tunnel, no collector data HTTP endpoint, no Rithmic HTTP proxy in web, and no liquidity polling in the browser. The old RITHMIC_DEPTH_URL/TOKEN env entries are removed from both mirrored web patches. The dev-only alignment and gateway flags are enabled together; the init schema provisioner's flag mirrors the alignment main container. Generated service slices are regenerated from the monolithic dev overlay. Production manifests/flags stay unchanged.

Collector credentials are injected only into its pod from Kubernetes Secret rithmic-depth-bridge. The source Kafka and registry endpoints are pinned to ES4; the two mirror destinations have pinned cluster identities. All three registries resolve the canonical raw/display schema under fixed ID 3301. Raw topics use one partition, RF1, delete cleanup and 24-hour retention on dev (declared in scripts/kafka/topics.env). The rithmic-depth-bridge-release job (Jenkinsfile.rithmic-depth-bridge-release; it was a branch of es4-deploy's ACTION=deploy-service SERVICE=rithmic-depth-bridge until 2026-11-08, and es4-deploy now refuses that path and names it) binds deploy, collector and contracts main revisions, provisions only the new topics/schemas, builds and pins its image digest, retires the superseded Mac collector/tunnel, then waits for acknowledged-book readiness. It exposes no Service or listening market-data port.

Build gateway with option-edge-feed-gateway (Jenkinsfile), not feed-gateway-deploy (Jenkinsfile.deploy, the retired host-jar topology). Build alignment through options-edge-processing with BUILD_TARGET=options-edge-es-spx-align. Build web through options-edge-web-deploy. Use the existing service-deploy job for separate web/gateway/alignment workload rollouts, binding the exact deployment main SHA and each image receipt. On the laptop CI agent select /Users/abhinav/.kube/jenkins-deployer-dev-remote.kubeconfig explicitly: its default localhost kubeconfig is stale. Production receives the raw mirrored Rithmic Test topic only; no production application rollout is requested.

Actual pod login, canonical Kafka records, gateway WebSocket events, chart gestures, stale/disconnect behavior and the same-contract Bookmap comparison are acceptance gates, not implied by source checks. Feed is labelled Rithmic Test. Bugzilla is skipped at the owner's request.

ES4 clean-reset restores the canonical source schema at fixed ID 3301 before producer/mirror replicas resume. Dev clean preserves the externally mirrored raw topic (still bounded by its 24-hour retention), avoiding topic deletion/auto-creation while the ES4 writer remains active. The display topic remains rebuildable.
