Design source of truth: `options-edge-processing` → `docs/es-future-options/GATE-2-SERVICE-DESIGNS.md`
(Gate-2, USER-approved 2026-07-12). Codex architecture decisions D1–D5 recorded there (§0.2).

## Shape

| Piece | Where | How |
|---|---|---|
| App services (18) | k3s single node on `.4` | `k8s/es4/services/*.yaml`, generated by `scripts/es4/render_es4_manifests.py` from the **production** slices; deployed digest-pinned by `Jenkinsfile.es4-deploy` |

## The es. prefix — one mechanism

Processing services get **every** topic es.-prefixed via `TOPIC_PREFIX=es.`
(`RuntimeProfileConfig.topic` prefixes compiled defaults AND env-supplied values), and
distinct Streams app-ids via `KAFKA_APPLICATION_ID_SUFFIX=-es4`. Both live in the
`es4-common-env` ConfigMap. The es-feed (Python, no prefix facility) sets explicit
es.-prefixed topic envs in its manifest.

Naming note: prefixed defaults keep their legacy tokens (e.g. `es.options.opra.tcbbo`
carries GLBX data — the "opra" token is the consumers' compiled default; cosmetic).

## SPX non-regression

This environment touches **zero** SPX deploy files: no `services.yaml` change, no
`k8s/services/**` change, no `Jenkinsfile.service-deploy` change, no shared-profile
change. The prod cluster holds NO es4 component: the es-feed Deployment that used to live there was deleted 2026-07-25 (DBP-R33). Previously it ran there (own pod,
resource-limited; the SPX feed Deployment is not modified).

  the OI baseline provider builds OPRA/OSI symbology that doesn't apply to GLBX; ES uses

## Runbook

1. `es4-deploy` ACTION=`infra-sync` — k3s + registries.yaml + compose stack + topics + ns/secret.
2. Copy the kubeconfig once: `scp 192.168.100.4:/home/es4/es4.kubeconfig ~/.kube/es4.kubeconfig`.
3. `es4-deploy` ACTION=`deploy-all` (or `deploy-service` + SERVICE).
4. es-feed: `es4-deploy` ACTION=`deploy-service` SERVICE=`es-feed` (applies at replicas 0), then
   ACTION=`activate-es-feed` with `ES_FEED_LOCATION=es4` and `ES_FEED_ACK_OI_AND_CAPACITY=true` to
   start it. Activation is deliberately separate so no deploy can raise a Databento session as a
   side effect. Stop it with ACTION=`deactivate-es-feed`.
5. Verify: `kubectl --kubeconfig ~/.kube/es4.kubeconfig -n options-edge get pods`;
   on `.4`: `docker exec es4-kafka kafka-topics --bootstrap-server localhost:29092 --list | grep ^es\\.`
