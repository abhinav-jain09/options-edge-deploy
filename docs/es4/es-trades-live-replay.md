# ES futures replay refresh

`es4-deploy` action `refresh-es-replay` builds the exact reviewed feed `main` commit in `FEED_PERMITTED_SHA`, on the Mac CI agent. `PERMITTED_SHA` separately binds this deployment repository. `REPLAY_TARGET=production` selects the ES4 singleton `es-feed` (Linux amd64, registry `192.168.100.252:5000`); `dev` selects its independent native ES subscription in `options-edge-databento-feed` (Linux arm64, registry `host.docker.internal:5001`). Each is a separate Jenkins run. Both namespace identities are pinned; production also checks exclusive ES4 placement (`Jenkinsfile.es4-deploy:34`, `Jenkinsfile.es4-deploy:107`, `scripts/es4/refresh-es-replay.py:163`).

Before image publication the action runs Rust and rollout tests and a read-only real Databento replay comparison against that environment's Kafka prefix. The Secret API key stays in memory and reaches only the diagnostic binary through its environment, never cargo build or argv. Output is redacted. The diagnostic has no producer, DB writer, offset commit or Kubernetes mutation. An empty rolling hour (including weekends) refuses the refresh (`scripts/es4/run-es-replay-shadow.py:1`).

The running singleton Recreate template is copied. Only its immutable image and explicit `DATABENTO_ES_TRADES_REPLAY_START_MINUTES=60` override change; no ConfigMap or replica-count apply occurs. The dev overlay and generated feed slice retain the replay setting. No experiment deployment exists (`scripts/es4/refresh-es-replay.py:163`, `k8s/overlays/dev/databento-feed-dev-patch.yaml:57`).

Acceptance requires the exact target-platform image/source, one ready pod with zero restarts, a 60-minute subscription, every saved unique identity matched on completion, and at least 60 seconds of stable observation. Active downstream Deployment pods must remain ready with unchanged identity/restart counts, and active source-topic Kafka groups must commit past the per-partition high offsets captured once after feed-side acceptance. Live traffic may continue accumulating newer offsets. Manually assigned consumers without active group membership are covered by pod health, not committed-group lag. Paused services are not started or claimed healthy. Reconnect loops fail (`scripts/es4/refresh-es-replay.py:110`, `scripts/es4/refresh-es-replay.py:163`).

After acceptance the action promotes the exact verified manifest bytes to the ES-only `es-replay` tag in that target registry. Shared `prod` and `dev` tags remain unchanged. The hand-authored ES4 manifest retains its existing `prod` reference until a dedicated tag is initialized; clean-reset and other existing manifest paths therefore remain resolvable before the first refresh. Those paths can select a different release; repeat this exact guarded refresh to select the replay-enabled artifact (`scripts/es4/refresh-es-replay.py:41`, `k8s/es4/services/es-feed.yaml:60`).

Failure or SIGTERM restores only this action's old template, with bounded concurrency-aware GET/patch retries and rollout verification. Competing rollouts are never overwritten. A hard kill or host failure cannot guarantee recovery. Registry promotion and template recovery are not transactional: a transport failure after PUT may leave the ES-only tag on the already verified image. Recovery does not remove published records. Global timeout is 180 minutes, build 120 minutes, rollout 45 minutes (`Jenkinsfile.es4-deploy:64`).

Production's pre-refresh feed is the August Python image. All 38 embedded and installed module hashes match reference commit `6c22ea59ddfdb9f54f030d44f56eb23eb3c264e5`; it has no OCI revision label. This refresh upgrades it to current Rust `main`, including the intervening main-line release changes. Its old registry manifest is no longer available; bounded recovery relies on its existing complete image cache and `IfNotPresent` policy on the ES4 node. This does not guarantee recovery after node/cache loss. Dev's old image remains registry-readable. The observed registry-host timer prunes Docker images/build cache, not registry tags or storage volumes; no registry tag-deletion job or matching cron/timer was found. Keeping a dedicated reachable tag protects the new digest from ordinary untagged-manifest collection; administrative deletion remains outside this action.

This maximum one-hour window recovers the restart gap. Ambiguous older prints are excluded, and replay prints older than two seconds cannot update live ES price or basis. Existing sealed/incomplete VWAP state is not rebuilt.

Consumer time semantics, offline opening-hour burst evidence and the distinction between active and paused workloads are recorded in `docs/es4/es-replay-consumer-audit.md:1`. Production ES4 disk preparation measured 27% filesystem use; its rollback image remains cached under `IfNotPresent`. The shared production registry's existing Docker prune timer does not remove registry storage volumes. These observations are preparation evidence, not a guarantee against external node/cache or registry deletion.

Before image publication and again immediately before the refresh, `validate-es-replay-settings.py` resolves the selected template's ConfigMap, Secret and literal environment in memory and passes it through stdin to `es-replay-settings`. The Rust diagnostic uses the actual `Settings::from_env_map` and `validate()`, lists enabled output topics, and describes them with topic auto-creation disabled. It has no publisher. Secret values are never written to artifacts or argv and are redacted from captured diagnostic output (`scripts/es4/validate-es-replay-settings.py:1`, feed `rust/examples/es-replay-settings.rs:1`). Both current environments passed, and a deliberately missing enabled DLQ topic was refused.

Replay completion is logged only after flushing the dedicated ES producer, so the offset fence includes the delivered replay burst. Committed offsets must reach that fixed fence; simultaneous zero live lag is not required. A tag promotion transport failure leaves the verified running feed in place and fails with an explicit unconfirmed-tag result; it never restarts that healthy feed (`scripts/es4/refresh-es-replay.py:125`, `:148`).

Digest bytes are verified cryptographically through index/manifest/config. The source binding is procedural: permitted-commit guard, unchanged-tree verification, the guarded build and its revision label. No source-signature claim is made. Linux amd64 emulation duration is not pre-benchmarked; the 120-minute build timeout fails before rollout. The builder's amd64 capability, local Docker endpoint, CPU and memory preparation were inspected. Deploy dev first, observe acceptance, then deploy production. Avoid the options-open transition; an options/VIX session restart can request another ES replay and deliberately fail a rollout's no-reconnect observation gate.

The deployment has two phases. Before any feed mutation, active groups must be Stable and must advance through a frozen current fence within sixty seconds. Phase A verifies the feed and can restore its old template on a feed-side failure. After that boundary, Phase B freezes the delivered replay fence and gives downstream consumers ten minutes to pass it. A downstream timeout, readiness failure or pod change fails the run without restoring the verified feed or promoting its tag. This prevents an unrelated consumer stall from creating another source gap (`scripts/es4/refresh-es-replay.py:133`, `:148`, `:163`). The feed selector is taken from the existing Deployment, rather than inferred from its name.
