## Runtime wiring

The existing broker-execution process serves its private JWT-authenticated API on port 8131. Its ClusterIP Service has no public ingress or NodePort. The web process proxies to `http://broker-execution-service:8131`, forwarding the original validated bearer and a separate shared credential. Dev uses the same dev issuer as the web deployment; production uses the production issuer. Browser mutation origins are explicit: local port 8090 in dev, `https://bleadingoptions.com` in production. There is no username/email/role allowlist. Existing database account grants and subject ownership remain required; deployment creates no grants.

HTTP `/health` is process health, used by startup/readiness/liveness probes. The trading readiness API separately checks the dispatcher, durable store, reconciled inventory, pinned account, broker session and upstream responsiveness. A healthy pod does not enable an order button by itself. No broker connection means an unavailable/red trading state, including production where no IBKR execution is expected. This change preserves the existing replica counts, PAPER mode, transmission setting, client IDs, source policies and account limits. It does not enable LIVE.

The new process explicitly requests 512 MiB and limits memory to 1 GiB, with a 512 MiB maximum Java heap and 128 MiB direct-memory bound. The remaining container budget is for metaspace, code cache, threads and native libraries. These are preparation settings, not measured throughput or soak claims. Permitted-host performance evidence remains a full-feature release gate; do not profile or load-test the Mac or production.

## Audit retention and operational capacity

All review/intent identities, broker-ID reservations, execution roots and their current corrections, private audit events and official results remain durable. No automatic deletion, ID reuse or loss of older trade access is introduced. The explicit external-state budget is 32 GiB per environment for the `broker_execution` schema, including table/index/TOAST sizes. `VISUAL_ORDER_STORE_BUDGET_BYTES` pins it in both manifests. The service samples PostgreSQL catalog sizes every 30 seconds and treats a sample older than 60 seconds as unavailable for new entries. A 70% warning appears in operational metrics; at 90%, new ENTER reviews, acceptance and final send are refused. Exits, cancellations, actual fills and corrections retain their accounting paths. The remaining 10% is operating headroom for existing exposure and reconciliation, not an assurance against a physically full database caused by unrelated writers.

A planning envelope of 30,000 trades with 100 private events each at a 4 KiB average is about 11.45 GiB of event payload. Allowing a factor of two for PostgreSQL/index overhead plus 2 GiB for commands, reviews, execution/alert state puts that envelope near 25 GiB. These are explicit sizing assumptions rather than measured traffic or a throughput promise; the actual measured byte quota controls admission if the distribution is larger. Review storage growth at the 70% warning and increase provisioned capacity/budget through reviewed configuration before the entry stop. No automatic archival facility is claimed. The dev host's read-only filesystem observation on 17 October 2026 showed over 500 GiB available; deployment must separately verify the production data volume and current schema usage.

`GET /internal/metrics` exposes aggregate callback/quote processing, lag, alert-delivery and audit-budget counters. It requires the shared service credential, rejects browser Origin/Cookie access and is not proxied as a user feature. It exports no account settings or private trade identities. Process `/health` stays distinct. B3 unknown-order, failed-close, unbalanced/uncovered and expired-exposure notifications persist in the execution database and use the existing canonical Avro status publisher. Notification statuses are explicitly nonterminal and bypass the intent recorder. Delivery runs outside the native reader, retries with backoff up to 12 consecutive failures per runtime instance and retains pending work across restart; exhausted delivery keeps execution readiness unavailable. Operator recovery uses the normal guarded Jenkins restart/deploy path after repairing the publisher. Resolved notifications retain the same alert key with a newer revision. They are never broker fill/cancel evidence.

## Shared credential

Shared infrastructure owns Secret `context-tape-execution-auth`, key `token`. Both deployments reference it without copying secret material into Git or rendered workload manifests. `ensure-context-tape-execution-auth.sh` preserves a valid existing credential, refuses malformed data and creates a random credential only when absent. It never rotates one implicitly. Generation requires the permitted Jenkins guard and job identity, uses a private temporary file, removes that file on exit and prints no credential. A failed read cannot be treated as absence; a failed create must be followed by a valid canonical read.

`common-infra-deploy` supports `CONTEXT_TAPE_AUTH_ONLY=true`. After the normal main/SHA guard, this mode validates the credential plan and, only with `DEPLOY_DRY_RUN=false`, creates it if missing. Production retains an explicit Jenkins input gate. All ordinary manifest, PVC and realm stages are skipped in this mode. It allows credential preparation without applying unrelated shared infrastructure. Normal shared-infra runs also prepare the credential, while their dry-run mode changes nothing.

## First-start order initialization

Common-infra runs [71](http://localhost:8085/job/common-infra-deploy/71/) and [72](http://localhost:8085/job/common-infra-deploy/72/) created/validated the shared credential in dev and production. New mode `CONTEXT_TAPE_ORDER_INIT_ONLY=true` in PR#1244 is mutually exclusive with credential-only mode and skips every ordinary infrastructure/realm/workload stage. Dry-run defaults true. `CONTRACTS_PERMITTED_SHA` is independently checked out/guarded on main and tree-verified before apply. Production has a ten-minute input gate. Each initializer invocation has a20-minute bound within the existing30-minute whole-job deadline; that global deadline remains binding and can stop a partially completed apply.

Pre-incident read-only observations found both dev order topics at earliest/end0, unbounded byte retention, and missing canonical subjects. Production order topics/subjects were absent. Raw IBKR schema identities were dev2/production40. Those snapshots are not substitutes for the script's fresh checks.

Before the first write, the initializer checks both order topics and subjects, target cluster endpoints, zero desired/actual executor/AMT bridge replicas, no matching pods (including terminating pods), and absent/inactive configured execution groups. It derives matchLabels from each Deployment and refuses empty selectors or unsupported matchExpressions. The CLI header must end in STATE/#MEMBERS; Empty classic groups with a blank assignment strategy are supported. Unknown output fails closed. Earliest and end offsets must be exactly partition0/offset0. No populated or already-used stream is accepted.

Missing topics are created as one partition/RF1, delete cleanup, unlimited time retention,1GiB byte retention, minISR1, max message1048588bytes. An empty existing topic with retention.bytes=-1 receives only the declared1GiB cap; no other existing policy is reconciled. Quiescence/emptiness are repeated before writes. Existing matching schemas are preserved; missing subjects register canonical source files. Deleted historical versions or incompatible schemas refuse by default. Schema Registry can omit redundant inherited namespaces, so raw object differences use its official **read-only** `POST /subjects/<subject>` identity lookup, requiring canonical source and current latest subject/id/version. Registration is the distinct `/versions` endpoint. No Avro parser or record conversion is implemented here.

Checks cover the executor and AMT/EAV bridge deployments/groups; they are not a Kafka-wide writer lock. External producers must remain stopped throughout. A later failure leaves earlier successful creates/registrations/configuration; inspect current state and Jenkins logs before any separately approved retry. Post-registration visibility uses up to20 reads and never retries a write blindly.
